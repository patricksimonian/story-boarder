# Authoring Review, Validation, and AI Suggestions in Refined Story Tools

Research ticket: *Before speccing a "model coach" (an AI review of authored scenes/notes that suggests structural changes — above all "this prose implies state you should track as a variable"), sanity-check what refined tools actually do: their static validation, their AI features, their privacy handling, and any prior art for inferring state from prose.*

Date: 2026-09-02. Audience: the later session that specs the model coach. Every claim carries its primary source inline; where a vendor's docs don't say, that's recorded rather than papered over. Compiler message strings quoted below were taken from raw source files and are exact; quotes from documentation pages came through a summarizing fetcher — faithful, but worth spot-checking at the cited URL before quoting verbatim anywhere that matters.

---

## 1. Static validation refined tools ship

The short version: every serious branching-narrative tool validates *referential integrity* (does this link/divert/jump point at something real?) and *script correctness* (does this expression parse and type-check?), the better ones validate *flow completeness* (does the story run out of content anywhere?), and none of them look at prose at all. Presentation converges on three patterns: compile-time console/issue lists, live editor diagnostics via a language server, and markers drawn on the graph itself.

### Ink / inklecate / Inky

The compiler distinguishes errors, warnings, and author TODOs. From the compiler source and official docs:

**Errors (compile fails):**

- **Diverts to unknown or misused targets**: `"target not found: '<target>'"`, plus a family of related checks — calling a non-function knot as a function (`"...hasn't been marked as a function, but it's being called as one. Do you need to delcare the knot as '== function X =='?"` — the typo is in the source), diverting to something marked as a function, wrong argument counts, external-function arity mismatches ([compiler/ParsedHierarchy/Divert.cs](https://github.com/inkle/ink/blob/master/compiler/ParsedHierarchy/Divert.cs)).
- **Name collisions and redefinitions**: redefined CONSTs, duplicate EXTERNAL declarations, ambiguous list item names, names colliding with reserved keywords or built-ins, knot/stitch/variable/list/argument clashes via a shared `NameConflictError` path ([compiler/ParsedHierarchy/Story.cs](https://github.com/inkle/ink/blob/master/compiler/ParsedHierarchy/Story.cs)).
- **Structural flow errors**: return outside a function, functions containing stitches/diverts/choices (`"Functions may not contain choices, but saw ..."`), duplicate flow names and parameter names ([compiler/ParsedHierarchy/FlowBase.cs](https://github.com/inkle/ink/blob/master/compiler/ParsedHierarchy/FlowBase.cs)); duplicate gather/choice labels, choices nested in conditionals that don't divert afterwards ([compiler/ParsedHierarchy/Weave.cs](https://github.com/inkle/ink/blob/master/compiler/ParsedHierarchy/Weave.cs)).

**Warnings:**

- **Loose ends** — the signature ink check: `"Apparent loose end exists where the flow runs out. Do you need a '-> DONE' statement, choice or divert?"` (FlowBase.cs above; [Writing with ink](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md) shows the compile-time form and the matching runtime error `ran out of content. Do you need a '-> DONE' or '-> END'?`).
- **TODOs**: a line starting `TODO:` is a first-class comment type "for reminding the author what they need to do, that the compiler prints out during compilation" (Writing with ink, "Comments" section) — internally an `AuthorWarning` parse object routed through the compiler's warning channel ([compiler/ParsedHierarchy/AuthorWarning.cs](https://github.com/inkle/ink/blob/master/compiler/ParsedHierarchy/AuthorWarning.cs)). The author annotates their own unfinished work and the toolchain carries the annotation forward on every compile.
- **Unused variables**: no such check could be confirmed — nothing in Writing with ink and nothing in the compiler files inspected. Ink appears not to warn on unused variables.

**Presentation.** Inklecate is a CLI printing line-numbered ERROR/WARNING/TODO messages. Inky, the official editor, recompiles constantly ("as-you-type error highlighting") and ships an **Issue Browser** that "lists errors, warnings and TODOs in your ink, and allows you to jump to the exact line number and file in the source" ([Inky README](https://github.com/inkle/inky)). Runtime integrations receive diagnostics via `onError` with `Ink.ErrorType.Warning`/`Error` ([RunningYourInk.md](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)). Ink's docs also lean on a *non*-tooling argument: weave syntax means "the output text can be easily skim read. That means there's no need to actually test all the branches in game to be sure they work as intended" (Writing with ink). Readability-as-validation is a stated design position.

### Yarn Spinner

The most thoroughly documented validator in this survey, with a formal three-tier severity taxonomy and — since v3.2.0 — stable error codes "for use with editor tools like Yarn Spinner for Visual Studio Code" ([YarnSpinner releases](https://github.com/YarnSpinnerTool/YarnSpinner/releases)). From the official [error-code reference](https://docs.yarnspinner.dev/write-yarn-scripts/yarn-spinner-editor/errors):

- **Errors** (block compilation): YS0001 conflicting implicit type declarations, YS0002 type mismatch (Yarn is statically typed), YS0012 jump to undefined node, YS0013 invalid function call, plus a long tail — duplicate node titles, unclosed commands/scopes, "can't infer variable type," variable redeclaration, enum misuse, syntax errors.
- **Warnings** (compile anyway, editor squiggle): YS0003 undeclared variable (reduced to "hint" severity in v3.1.0 per the release notes), YS0008 unreachable code, YS0015 cyclic node dependency, plus "unknown character" (a speaker name not defined in the project). v2.4.2 added a warning for each empty node.
- **Info**: YS0010 unused variable — "declared but never used anywhere."

There is also a separate post-compilation **Analyser API**: `Yarn.Analysis` ships a `VariableLister` and an `UnusedVariableChecker` that reports `"Variable X is assigned, but never read from"` at Warning severity, each `Diagnosis` carrying message, node, line/column, and severity ([YarnSpinner/Analyser.cs](https://github.com/YarnSpinnerTool/YarnSpinner/blob/main/YarnSpinner/Analyser.cs)).

Undeclared variables get inferred types and default values (zero, false, empty string), but the language server flags them and the docs recommend explicit `<<declare>>` ([Logic and variables](https://docs.yarnspinner.dev/write-yarn-scripts/scripting-fundamentals/logic-and-variables)). **Presentation**: the VS Code language server "validates scripts in real time"; "errors and warnings appear as squiggly underlines in the editor and in the Problems panel," alongside a graph view of nodes and hover info showing a variable's type, default, and doc comment ([Writing Yarn in VS Code](https://docs.yarnspinner.dev/write-yarn-scripts/yarn-spinner-editor/writing-yarn-in-vs-code)).

### articy:draft (3 and X)

articy validates as a database, not a compiler. The Navigator has a dedicated **Conflicts tab**: a search form over six check categories, returning "all objects where at least one of the specified conflicts occurs" ([X help](https://www.articy.com/help/adx/UI_Conflicts.html); [3 help](https://www.articy.com/help/UI_Conflicts.html); [overview](https://www.articy.com/en/adx_basics_search/)):

1. **Invalid property values** — template fields violating their declared rules (text length, numeric range); also "clearly marked in the properties view."
2. **Duplicate technical names** — a technical name "should be used only once throughout the entire project."
3. **Script errors** — in pins and Condition/Instruction nodes (expresso scripts).
4. **Invalid references** — the standout design decision: when a referenced object is deleted (say, an entity used as a dialogue speaker), the reference "is not entirely removed but set to an 'invalid' state," so the conflict search can find every object pointing at the corpse rather than silently losing the link.
5. **Defective assets** — imports that failed after five attempts.
6. **Localization errors** — a property filled in the primary language but empty in a secondary, or vice versa.

Searches can be scoped to a project section; results are transient (not saved with the project). Scripts also get live checking in the editor itself: an option "activates the auto-completion, syntax highlighting and error detection for all pin labels and other script textboxes," and "conflicts in the script are visualized by words underlined in red and the conflict icon in the upper right. Hovering over the icon will show a tooltip describing the conflict" ([Scripting in articy](https://www.articy.com/help/adx/Scripting_in_articy.html)). A feature literally named "Verify Scripts" / "Script Verification" could not be confirmed — script checking is delivered through Conflict Search plus the inline editor checks.

### Twine ecosystem

Twine 2 itself is famously permissive — the serious linting lives in community tooling:

- **The Twine 2 editor**: broken-link detection is visual, on the story map — "if there is a link in a passage that Twine can't find a passage for, it will instead show a red line ending in a 'no entry' symbol" ([twinejs docs, navigating](https://github.com/klembot/twinejs/blob/develop/docs/en/src/editing-stories/navigating.md)); the Story Details dialog reports "the number of links and broken links in your story" as a statistic ([twinejs docs, stats](https://github.com/klembot/twinejs/blob/develop/docs/en/src/editing-stories/stats.md), backed by a `brokenLinks` getter in [src/store/stories/getters.ts](https://github.com/klembot/twinejs/blob/develop/src/store/stories/getters.ts)). That's the extent of it — no text diagnostics, no issues panel.
- **Tweego**, the standard Twee compiler: its [docs](https://www.motoslave.net/tweego/docs/) describe no error reporting at all (they cover usage only, plus auto-generation of missing IFIDs and metadata). The source does emit load-level diagnostics to stderr — malformed twee metadata, passages with no name, `"warning: Replacing existing passage %q with duplicate."`, StoryData unmarshal failures, IFID validation ([storyload.go](https://github.com/tmedwards/tweego/blob/master/storyload.go), [story.go](https://github.com/tmedwards/tweego/blob/master/story.go)) — but nothing checks links or story structure.
- **Extwee**: no validation or error reporting beyond parse failures could be confirmed from its [README](https://github.com/videlais/extwee).
- **Twee 3 Language Tools** (T3LT, the de facto Twee IDE as a VS Code extension) is where linting happens ([README](https://github.com/cyrusfirheir/twee3-language-tools)): warnings for `[[passage]]` links "when `passage` is not a valid passage name" (with an acknowledged false-positive case around variables-as-link-targets), and a deep SugarCube-2 layer — mismatched macro open/close tags, deprecated macros with suggested alternatives, deprecated `<<end...>>` syntax with a quick-fix, unrecognized/undefined macros (toggleable, quick-fix writes a definition to the workspace config), invalid argument syntax, and full macro argument validation. Harlowe and Chapbook get syntax highlighting only. Presentation is standard VS Code: squiggles, Problems panel, quick-fixes.
- **Harlowe**, for contrast, validates at *runtime*: errors appear in the running story, and Debug Mode adds an "Errors" drawer listing "all of the errors that have appeared in the story thus far," plus a replay button showing "a step-by-step view of how the macro call's code was interpreted" ([Harlowe 3.3.8 manual](https://twine2.neocities.org/)). No first-party authoring-time Harlowe linter was found.

The pattern worth noting: the *format-agnostic* layer (Twine, Tweego) validates nearly nothing because macro semantics belong to the story format; the linting had to move to a tool that commits to one format's semantics.

### Arcweave

The only validation confirmable from official docs is arcscript compile-error marking: "when a script has a compile-time error, this is denoted by an exclamation mark symbol, at the lower right corner of the container element," with details on hover ([Arcscript docs](https://docs.arcweave.com/project-items/arcscript)). Could not confirm any unreachable-element detection, broken-connection checking, or project-wide consistency report anywhere in docs.arcweave.com.

### Cross-tool observations

Only Yarn Spinner has a formal severity taxonomy with stable codes; ink's near-equivalent trio is error/warning/TODO. The unused-variable check exists first-party only in Yarn Spinner (YS0010 plus the runtime `UnusedVariableChecker`); ink and the Twine ecosystem don't ship one. Reachability: Yarn flags unreachable code and cyclic dependencies; ink attacks the inverse problem (loose ends — flow that runs out); nobody in the Twine ecosystem or Arcweave flags unreachable passages/elements first-party. Nobody validates prose.

## 2. Model/AI-driven review of authored content

The framing throughout: **generate** (writes new content) vs **critique** (reviews existing content) vs **structure-suggest** (proposes variables/flags/entities/state to track). Answer up front: generation is everywhere, critique exists in a handful of refined forms, and **no shipped tool's AI says "track this as a variable."**

### Arcweave — generation plus a chat sidebar that will look for plot holes

Four AI tools ([overview](https://docs.arcweave.com/project-tools/ai-features/overview)): **Element Generator** (right-click an element → AI → "Generate element," prompt up to 200 characters with @-mentions of components; creates one new element "with a suggested title, content, and component mentions," auto-connected to the source, reading preceding elements for context — elements only, never branches, connections, or variables — [element-generator doc](https://docs.arcweave.com/project-tools/ai-features/element-generator)); **Element Enhancer** (rewrites existing element content); **Image Generator**; and the **Design Assistant** — a chat sidebar that answers questions about your project, Arcweave functionality, and Arcscript, and explicitly "does not generate elements or branches on the board." The docs' own example prompts include **"Do you find any plot holes?"** ([design-assistant doc](https://docs.arcweave.com/project-tools/ai-features/design-assistant)) — so Arcweave first-party documents critique-by-chat, as an informal Q&A capability rather than a structured review feature. Nothing has it recommending variables, conditions, or components. Their [AI approach page](https://arcweave.com/ai) is philosophy and data governance ("AI is a tool to support, not replace, human creativity"; no training on user data), and the [roadmap](https://arcweave.com/roadmap)'s only AI item is image-reference assets. **Verdict: generation plus an informal chat critique channel; no structure suggestion.**

### articy:draft X — purely generative, explicitly bolt-on

AI arrived in version 4.0.0 as **AI Extensions**: "with the use of third party AI services you get access to AI assisted barks, dialogues, and preview images" — generation only, driven from a selected dialogue/flow fragment; 4.2.0 added a **VO Extension** (ElevenLabs synthesis of existing lines), and admins can disable the whole plugin ([What's New](https://www.articy.com/help/adx/WhatsNew.html); [feature list](https://www.articy.com/en/articydraft/feature-list/); [4.2 announcement](https://www.articy.com/en/whats-new-in-articydraft-x-4-2/)). You connect *your own* OpenAI account and are "obliged to enter into your own contract with the provider"; "Articy does not collect, analyze, or use any data that you send to such Third Party Services" ([AI Extensions help](https://www.articy.com/help/adx/Services_AI.html)). **Verdict: generation only — the absence of review features is confirmed from their own changelog.**

### Sudowrite — the clearest split between structure, generation, and critique

- **Story Bible** is a chain of structured fields — Braindump, Genre, Style, Synopsis, Characters, Worldbuilding, Outline, Scenes — that "gathers the core elements of your story in one place so that you and Sudowrite's AI can reference them," where "any section can be manually populated to any degree — but some sections also feature a Generate button," each field feeding generation of the next ([What is Story Bible](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/what-is-story-bible/jmWepHcQdJetNrE991fjJC)). Notably **unidirectional**: the docs never describe extracting characters or world elements *from* prose the author wrote.
- **Feedback** is genuine AI critique: it "reads your work and leaves comments in the margin, just like a real editor — except it also sees your Story Bible," each comment carrying "a specific observation and a suggested next step — a rewrite, a question to consider, or a craft note." Modes span Developmental ("pacing, structure, character arcs, plot holes"), Line, Dialogue, Copy Edits, custom types, and a **Beta Read** with three AI reader personas (Maya: emotional resonance; Anton: structure, pacing, motivation; Joan: plausibility breaks) ([Feedback docs](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/feedback/7Ew1KgpEwabQSgvijq8QNr)). Professional/Max plans only.
- **State-adjacent machinery**: [Chapter Continuity](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/chapter-continuity/4KL8gFeLZQ6GSBjDWtSbV6) sequences documents so generation treats them as one continuous story; the **Saliency Engine** "decides whether or not story context elements from Character and Worldbuilding cards are relevant to the task at hand," with per-card [visibility settings](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/visibility-settings/4KL8gFeLZP6ep8keUhKVGp) to override it. That's AI *selecting from* manually maintained state, not suggesting state to create.

**Verdict: real margin-comment critique grounded in the author's own bible — but its vocabulary is editorial (pacing, motivation, plausibility), never structural in the game-state sense.**

### NovelAI — generation plus a manual keyed state store

The **Lorebook** is entirely manual: entries whose text is inserted into context "when an activation key is found in the recent context," with case-sensitivity markers, regex, `&` compound keys, Always On, cascading activation, and fine placement controls ([Lorebook docs](https://docs.novelai.net/en/text/lorebook/)). A **Lorebook Generator** will draft entry *content* from a description plus story context — AI populating a store the human decided to create. No review/critique feature and nothing that suggests what to track: confirmed absence from the docs.

### Campfire — could not confirm any AI feature

Campfire's own product page lists sixteen modules with no mention of AI anywhere ([campfirewriting.com/write](https://www.campfirewriting.com/write)); searches across their site found no AI announcement, feature page, or position statement. Third-party review sites claim "AI-assisted drafting," but that fails the primary-source bar. Recorded as: no AI features confirmable from the vendor's own site.

### World Anvil — first-party declination

World Anvil's official response to an "AI Novel Writer" community suggestion: **"AI features are not within the scope of World Anvil and, therefore, we're declining this feature"** ([suggestion page](https://www.worldanvil.com/community/voting/suggestion/182ee13a-ceb8-4bb8-b53d-904bfb2a326e/view) — surfaced via search snippet; the page 403s non-browser fetches). Per search results their FAQ also states they don't train AI models on user work, but the page could not be fetched directly. No fuller position document could be located.

### Novelcrafter — the closest structural machinery, and the detection isn't AI

The **Codex** "automatically indexes every mention of your characters, places, and objects directly inside your text" with "Smart Detection" of names and aliases as you type ([codex feature page](https://www.novelcrafter.com/features/codex)) — but that's string matching against entries the author already created; the Tracking tab controls detection, highlighting, a mentions heatmap, and "whether the entry is always sent to the AI, only when detected, or never" ([Anatomy of a Codex Entry](https://www.novelcrafter.com/help/docs/codex/anatomy-codex-entry)). The **Extract** feature converts AI chat output into Codex entries, chapters, or scene beats — "take the responses and generate codex entries from them" — but it's user-initiated and pattern-based ("designed to be tolerant of different formats," working best with a `Name (aliases) [tags]: description` convention), not the AI spotting entities in your prose and proposing them ([Extract doc](https://www.novelcrafter.com/help/docs/organization/the-extract-feature)); their [changelog](https://feedback.novelcrafter.com/changelog) also records a "Detect Characters" capability. Chat can be asked "about anything inside of your story" — informal critique-by-chat, the same shape as Arcweave's assistant.

### Manuscript-analysis tools — critique at scale, no state

- **Marlowe / Authors.ai** — pure critique, explicitly anti-generative: "No generation, ever — Marlowe's architecture is built for analysis, not text generation." Whole-manuscript analysis of plot structure, character development and consistency, pacing, dialogue balance, and themes, delivered as a report/dashboard with beat-placement graphs ([authors.ai/marlowe](https://authors.ai/marlowe/)).
- **ProWritingAid** goes well past grammar: **Manuscript Analysis** (up to 300k words; a report "of characters, plot, and setting, prioritized by importance," including plot inconsistencies, character consistency, pacing, structural flaws) and **Chapter Critique** (including "a beat-level outline of your narrative") ([Manuscript Analysis help](https://help.prowritingaid.com/article/318-what-is-the-manuscript-analysis); [Critique report help](https://help.prowritingaid.com/article/270-what-is-the-critique-report)). Report-shaped critique; no state suggestions.
- **Fictionary StoryTeller** — the strongest "prose implies state" example found, though the schema is the tool's, not the author's: on import it "scans the manuscript and creates an initial Cast of Characters, links characters to scenes, sets the POV character for each scene, draws the Story Arc," which the author then reviews and corrects against Fictionary's fixed 38 story elements in a Story Map ([fictionary.co/products/storyteller](https://fictionary.co/products/storyteller/) — content via search snippets; the site 403s direct fetches). Automated extraction of trackable entities and per-scene state *from* authored prose, in service of critique — into a fixed editorial schema rather than author-defined variables.

### Quality-based narrative prior art — qualities were always hand-declared

StoryNexus, Failbetter's authoring platform, built worlds from "storylets, qualities, areas, settings and characters," using "the same tools we've been using for years to build and maintain Fallen London" ([Dev diary #1](https://www.failbettergames.com/storynexus-developer-diary-1-worlds-exist/); [Dev diary #2](https://www.failbettergames.com/news/storynexus-developer-diary-2-fewer-spreadsheets-less-swearing) — "the simple rhythm of setup-choice-result … is the StoryNexus idiom"). Authors created every quality by hand; no tooling suggested them. Emily Short's definitional essay on QBN names the pain directly: the model "requires the author to track story progression very much by hand … you have to manually set a quality that corresponds to A being available; then another value meaning it's complete … It's a lot of bookkeeping for functionality that many other systems provide automatically" ([Beyond Branching, 2016](https://emshort.blog/2016/04/12/beyond-branching-quality-based-and-salience-based-narrative-structures/)). The bookkeeping burden was identified as a tooling gap in 2016; no tool has been found filling it since.

### Bottom line for question 2

Generation into human-defined structure: Arcweave, articy X, Sudowrite, NovelAI. Critique of existing content: Sudowrite Feedback (margin comments, bible-aware), Marlowe and ProWritingAid (whole-manuscript reports), plus informal critique-by-chat in Arcweave and Novelcrafter. Structure suggestion in the state-tracking sense: nothing. Two near-misses define the edges of the gap — Fictionary auto-extracts entities and per-scene state from prose but into its own fixed schema for linear-manuscript critique, and Novelcrafter's Extract turns text into trackable Codex entries but only when the user asks and only via format conventions. The intersection — AI-initiated, from the author's own prose, proposing author-owned state — appears in no commercial tool's first-party documentation. The absence is the finding.

## 3. Privacy and API keys in local-first tools that added AI

Four key-handling models show up, and local-first tools cluster hard on the first two.

**Bring-your-own-key** is the norm wherever the vendor doesn't want to be in the AI business: articy:draft X (connect your own OpenAI account; "Articy does not collect, analyze, or use any data that you send to such Third Party Services" — [AI Extensions help](https://www.articy.com/help/adx/Services_AI.html)); Novelcrafter, which is pure BYOK — "we currently do not offer any AI model ourselves" ([Does Novelcrafter provide its own AI?](https://www.novelcrafter.com/help/faq/ai-connections/does-novelcrafter-provide-its-own-ai)), with per-vendor connection docs for OpenAI, Claude, OpenRouter, and Ollama ([connections index](https://docs.novelcrafter.com/en/collections/7278587-connections)); and the Obsidian AI plugins below. SillyTavern is the BYO-everything existence proof: a locally installed frontend whose official docs list local backends (KoboldCpp, llama.cpp, Ollama, TabbyAPI) alongside cloud APIs, framing local as "free to use" and totally private — "everything you write stays on your own PC" ([API connections](https://docs.sillytavern.app/usage/api-connections/); [FAQ](https://docs.sillytavern.app/usage/faq/)). Keys land in a local `secrets.json`, hidden from the UI after saving; the multi-user docs warn plainly that in that mode chat history and keys "are stored in plain text on the server" ([multi-user](https://docs.sillytavern.app/administration/multi-user/)).

**Local models via Ollama/LM Studio** ride along with BYOK almost everywhere: Novelcrafter's Ollama doc shows the mechanics of a web app talking to a local model (whitelist the origin via `OLLAMA_ORIGINS`, and "Novelcrafter itself does not pull/add any AI models on its own" — [Ollama connection](https://www.novelcrafter.com/help/docs/ai-connections/ollama)), framing local as the option "if you don't want anyone/AI companies seeing your writing." Copilot for Obsidian supports cloud, local, and OpenAI-compatible providers, keys "stored in this device's Obsidian Keychain, not in the vault's `data.json`," pitching Ollama/LM Studio for "complete local privacy … nothing leaves your machine" ([obsidian-copilot](https://github.com/logancyang/obsidian-copilot)). Smart Connections goes further — "zero setup. No API key," "embeddings are created locally by default. Your notes stay on your machine" ([obsidian-smart-connections](https://github.com/brianpetro/obsidian-smart-connections)).

**Bundled cloud with account** is the commercial-writing-tool model: Sudowrite (subscription; the FAQ promises "we do not use your writing to train AI models" and names the third-party model pipeline — Anthropic, OpenAI, open-source, in-house — though notably the legal privacy policy repeats none of this; the strong promises live only in the [FAQ](https://sudowrite.com/faq)) and NovelAI (subscription; stories "are encrypted in your browser, so all story data at rest on our servers is encrypted and nobody but you can read your stories," with the honest carve-out that generation requests "will contain unencrypted bits of your story that are necessary for our AI to do its work," not stored or logged — [NovelAI FAQ](https://docs.novelai.net/en/faq/)).

**No AI, stated outright** is itself a documented position: Obsidian's core ships none — "your data is stored on your device, inaccessible to us" ([about](https://obsidian.md/about)); no standing first-party "we ship no AI" page could be confirmed, so that exact framing stays soft. Scrivener is categorical: "Scrivener itself contains no artificial intelligence" and "does not do anything with your text in the background that would cause it to be sent anywhere from your machine to any other server" — the AI prompts Mac users see are Apple Intelligence, injected by macOS, which "Scrivener cannot exclude" ([Literature & Latte blog](https://www.literatureandlatte.com/blog/scrivener-and-ai-why-do-i-see-ai-prompts-in-my-scrivener-projects-on-mac)).

### Disclosure and opt-in patterns

The strongest primary source here is Obsidian's **Developer Policies**, which make disclosure a directory-listing requirement — the following are "only allowed if clearly indicated in your README … Network use. Clearly explain which remote services are used and why they're needed," alongside required disclosure of payment, accounts, and server-side telemetry (with a linked privacy policy), and a flat ban on client-side telemetry ([Developer policies](https://docs.obsidian.md/community-directory/developer-policies)). Enforcement is delisting, not runtime consent — though their ["Future of plugins" post](https://obsidian.md/blog/future-of-plugins/) announces manifest-declared capabilities (network, file system, clipboard) that "users will be able to see … before installing plugins." Copilot for Obsidian's README demonstrates per-feature data-flow disclosure: which party (your configured provider vs. the vendor's backend) receives text, feature by feature, with retention and no-training terms for hosted requests. Zed documents the default-off pattern most precisely: "Zed does not retain your prompts or code context by default," retention only on explicit feedback or training opt-in, and exact statements of when keystrokes send context to a provider ([Zed AI privacy](https://zed.dev/docs/ai/privacy-and-security)). Across everything surveyed, no tool documents a runtime consent *dialog* — disclosure lives in READMEs, docs pages, and settings screens.

## 4. Prior art for inferring state-tracking from prose

The research world has been working the comprehension-side twin of the model-coach idea — read text, infer the state it implies — for years. Verified items, closest-fit first:

- **Story2Game** (Zhou, Basavatia, Siam, Chen, Riedl, 2025) — the single most on-target paper found. It generates a story with an LLM and then builds executable game code, and the abstract says the quiet part: "the key to successful action generation is to use LLM-generated preconditions and effects of actions in the stories as guides for what aspects of the game state must be tracked and changed." State-variable inference from story prose at authoring time — though the prose is machine-generated, not a human author's draft. [arXiv:2505.03547](https://arxiv.org/abs/2505.03547)
- **OpenPI** (Tandon et al., EMNLP 2020) — open-vocabulary entity state tracking: for each sentence of procedural text, predict (entity, attribute, before-state, after-state) tuples with no fixed schema, so the model must *invent* the attribute names — precisely the "what should be a variable here?" question. [ACL Anthology](https://aclanthology.org/2020.emnlp-main.520/); follow-up [OpenPI2.0](https://arxiv.org/abs/2305.14603) adds salience annotations — which matters for any tool that shouldn't propose fifty variables per scene.
- **ProPara** (Dalvi et al., NAACL 2018) — the foundational dataset: entity existence and location tracked through every step of natural paragraphs, framed around the fact that "the causal effects of actions are often implicit and need to be inferred." [ACL Anthology](https://aclanthology.org/N18-1144/)
- **JerichoWorld / Modeling Worlds in Text** (Ammanabrolu & Riedl, 2021) — 24,198 mappings from text-game observations to knowledge-graph world states plus valid actions; the at-scale benchmark for "read prose, emit world state." [arXiv:2106.09578](https://arxiv.org/abs/2106.09578); earlier, agents building knowledge graphs from observations alone in [Ammanabrolu & Riedl, NAACL 2019](https://aclanthology.org/N19-1358/). Infrastructure: [TextWorld](https://arxiv.org/abs/1806.11532), [Jericho](https://arxiv.org/abs/1909.05398).
- **Bringing Stories Alive** (Ammanabrolu et al., AIIDE 2020) — pre-LLM story-to-game: extract a partial knowledge graph (locations, objects) from an existing plot, fill gaps with commonsense, use it as the skeleton of a playable IF game. [arXiv:2001.10161](https://arxiv.org/abs/2001.10161)
- **GENEVA** (Leandro et al., Microsoft Research, IEEE CoG 2024) — GPT-4 turns a high-level story description plus constraints into a branching-and-reconverging narrative graph a designer can visualize; structure extraction rather than variable extraction, but the canonical "prose in, formal branching structure out" designer tool. [MSR publication page](https://www.microsoft.com/en-us/research/publication/geneva-generating-and-visualizing-branching-narratives-using-llms/)
- **StoryVerse** (Wang, Zhou, Ledo, FDG 2024) — co-authoring architecture where a game-environment proxy maintains an explicit list of world-state variables updated by LLM-simulated character actions; the variables are *declared*, not inferred. [arXiv:2405.13042](https://arxiv.org/abs/2405.13042). **Elsewise** (Wang, Chung, Roemmele et al., 2025) inverts the whole question: rules are written as condition and effect *in free-form natural language*, and the tool visualizes the resulting possibility space — prose *as* the state logic instead of state extracted from prose. [arXiv PDF](https://arxiv.org/pdf/2601.15295)
- **Consistency checking**: **SNaC** (Goyal, Li, Durrett, EMNLP 2022) — taxonomy plus 9.6K span-level annotations of coherence errors in long narrative summaries, with a classifier that localizes them ([ACL Anthology](https://aclanthology.org/2022.emnlp-main.29/)); **SCORE** (2025) — "Dynamic State Tracking" monitors objects and characters via symbolic logic while an LLM generates episodes, catching inconsistencies — state tracking deployed as a continuity linter ([arXiv:2503.23512](https://arxiv.org/abs/2503.23512)).
- **GitHub, verified by README**: [nosferathoo/generate_twine](https://github.com/nosferathoo/generate_twine) generates complete Twee/Twine stories from a prose gamebook description via local LLMs, then runs iterative *structural* repair — graph analysis finds missing passages, trap cycles, and dead ends, and the LLM patches them. It lints the story *graph*, not story *state*. [AventurasTeam/Aventuras](https://github.com/AventurasTeam/Aventuras) does runtime state inference from LLM-narrated play (who's present, where you are, what you carry) with an agent that consolidates lorebook entries. Searches for an Ink- or Yarn-specific LLM authoring assistant that extracts state turned up nothing substantive.

Failed verifications, for the record: no LLM-IF authoring tool named "Spindlewheel" exists (the name belongs to a card game); "Dungeons and Data" is a NetHack dataset, unrelated; nothing relevant found on intfiction.org in these searches.

**The gap, stated plainly:** nobody found does authoring-time "you should track this as a variable" on a *human author's* prose. OpenPI proves models can invent attribute names from open-domain text; JerichoWorld proves prose-to-world-state at scale; Story2Game derives trackable state from story prose but inside a machine-story-to-machine-game loop. Applying that extraction to authored scenes and surfacing it as suggestions appears genuinely unclaimed territory.

## What this means for the storyline app

Descriptive only — the spec discussion happens elsewhere.

The app's existing static analysis panel (unreachable scenes, dead branches, variables never set, dangling references) already covers the same ground as the strongest shipped validators: it sits closest to Yarn Spinner's warning tier (unreachable code, unused variable — the only first-party unused-variable check in the field) and articy's conflict search (invalid references), and ahead of Twine/Tweego, which validate almost nothing. The presentation patterns the refined tools converge on — a jump-to-source problems list (Inky's Issue Browser, Yarn's Problems panel), markers on the offending node (Arcweave's exclamation corner, Twine's no-entry arrow, articy's red underlines + hover tooltip), and articy's keep-broken-references-findable-instead-of-deleting move — are the established vocabulary a review surface would be read against. Ink's `TODO:` is the one author-annotation idea in the set: the author's own notes-to-self carried through every compile.

On the AI side, the model coach as imagined has no direct precedent, and the surrounding fragments map its edges precisely. Critique exists (Sudowrite's bible-aware margin comments; Marlowe and ProWritingAid's whole-manuscript reports; Arcweave's chat that will answer "do you find any plot holes?"), entity extraction from prose exists (Fictionary's import scan, into a fixed editorial schema; Novelcrafter's string-match codex detection and user-triggered Extract), and state-from-prose inference exists in research (OpenPI's invented attributes, Story2Game's preconditions-and-effects-as-state-guide). Nothing combines them. Emily Short named the manual-bookkeeping burden of quality-based narrative as a tooling gap in 2016, and the QBN tradition — hand-declared qualities gating storylets, the same shape as this app's variables gating storylets — has carried it unfilled since.

On privacy, the field's answer for local-first tools is consistent: bring-your-own-key with optional local models via Ollama/LM Studio (articy X, Novelcrafter, SillyTavern, the Obsidian plugin ecosystem), disclosure in docs rather than runtime dialogs, with Obsidian's developer policies ("clearly explain which remote services are used and why they're needed") as the cleanest codification and Zed's default-off retention statements as the most precise data-flow disclosure. Bundled-cloud is the model only for tools that *are* the AI service (Sudowrite, NovelAI).

One existing precedent inside this project rhymes with everything above: the Twine importer already lifts `if`/`set` macros into conditions and effects "as suggestions only, never silent conversion" (spec.md, import section). Every reviewed tool that touches the author's structure — Novelcrafter's Extract, Fictionary's review-and-correct import, articy's invalid-reference preservation — takes the same stance: propose, let the author confirm, never mutate silently.
